# Open Questions

Every unverified assumption and known implementation gap in this repo, consolidated in one
place. Numbers match `PLAN.md` §9 where that section already numbered an item, so
cross-references from code docstrings stay stable. Items 11-14 are new gaps discovered
during implementation, not present in `PLAN.md` §9.

| # | Question | Why it matters | Current stance | Owner / next step |
|---|---|---|---|---|
| 1 | Is `data_universe` the right package name? | The repo is `data-universe`, not a valid Python identifier. | Resolved as `data_universe`; install stays `pip install git+https://github.com/GTSF-Quantitative-Sector/data-universe.git`. | Flag only, in case a different name (e.g. `gtsf_quant`) is preferred. |
| 2 | Is `pyyaml` an acceptable core dependency? | Needed for `config.load_yaml()`; not in the original prompt's core requirements list. | Added to `setup.py`'s `install_requires`. | Flag only, in case TOML/env-only config is preferred instead. |
| 2b | Should FRED need its own API key/setter? | Not mentioned in the original prompt's config/env var list. | Added `FRED_API_KEY` / `config.set_fred_key()`. | Flag only. |
| 3 | Is daily-close-only sufficient for options, or is NBBO/quotes needed? | The prompt says to assume daily contract closes only, but also says full trades/NBBO "may be a separate add-on." | Built strictly against daily-close-only (`PolygonOptionsSource.daily_close`); `is_stale` exists because of this. No NBBO/quotes source attempted. | Ask before building an NBBO source speculatively. |
| 4 | Does the Polygon plan tier include indices access for `I:VIX`? | `iv_index` (feature, Phase 6) depends on `index_daily_bars("I:VIX", ...)` for its SPY path. | Built against the interface (`PolygonSource.index_daily_bars`); entitlement unconfirmed. | Confirm with whoever holds the Polygon plan; `OPEN_QUESTIONS.md` cross-referenced from `sources/polygon.py`. |
| 5 | Are the Polygon endpoint paths/fields used here correct? | Stock/index aggregates, options contract reference, options daily aggregates, and the flat-files S3 hostname were all written against documented conventions, not re-verified against live docs in this session. | Each is mocked in tests, never called against a live endpoint in CI. No hardcoded flat-files hostname default — must be set via `POLYGON_FLATFILES_ENDPOINT`. | Verify against live Polygon docs before the first real (non-fake) run in production. Cross-referenced from `sources/polygon_options.py`. |
| 6 | Is the EDGAR submissions JSON shape assumed here correct? | `EdgarSource.earnings_8k_filings` assumes `filings.recent.items` is a comma-separated string of Item numbers (e.g. `"2.02,9.01"`) for a given accession. | Written against that assumed shape, mocked in every test; not re-verified against live `data.sec.gov` docs. | Verify against a real submissions JSON response before relying on it in production. Cross-referenced from `sources/edgar.py`. |
| 7 | Is `sigma_pre`'s "30-day" window trading days or calendar days? | Changes every `sigma_pre_daily` value in the PEAD event table. | Taken as 30 **trading** days, consistent with every other "Nd" window in this library. | Confirm with the PEAD project team; `CONTRACTS.md` states this explicitly. |
| 7b | Is `(DTB3 / 100) / 252` the right risk-free-rate conversion? | Changes every `ret_excess_1d` value for the beta project. | `FredSource.daily_rate` currently divides the annualized percent by 100 then by 252 (trading days), with no bank-discount-to-bond-equivalent-yield conversion first. | Confirm the right day-count and discount/yield convention with the beta project team. Cross-referenced from `sources/fred.py`. |
| 8 | Whose schema wins — this repo's or vrp-research's? | `CONTRACTS.md` defines this repo's own long-format (`date, ticker, value`) schema and PEAD event table shape, not one handed down by another team. | Built as our own definition per the original prompt's instruction to propose one and ask others to reconcile. | vrp-research (and PEAD/beta as needed) should read `CONTRACTS.md` and flag any mismatch with their own existing schemas. |
| 9 | Should `setup.py` use `find_packages()` instead of an explicit list? | `sec_parser` lists `packages=["sec"]` explicitly (one package). This repo explicitly lists all 6 sub-packages instead of using `find_packages()`. | Explicit list kept, for the closest parity with `sec_parser`'s style while still covering every sub-package. | Flag only — no action needed unless `find_packages()` is preferred. |
| 10 | Does the Polygon plan tier include intraday hourly aggregates, and how far back? | The beta project wants hourly variants "if hourly bars are available." | Built against the interface (`PolygonSource.hourly_bars`, filtered to regular hours by `filter_regular_hours`); actual availability/history depth unconfirmed. | Confirm with whoever holds the Polygon plan. |
| 11 | Is `Ticker` (`PLAN.md` §3) still wanted? | `data_universe/ticker.py` does not exist. `__init__.py` does not export `Ticker`. Every `PLAN.md` README example line using `q.Ticker(...)` does not work today — this repo's own `README.md` documents the actual workaround instead. | Not built in any of Phases 1-7. Workaround: call `features.registry.compute()` / `labels.registry.compute()` directly with a `source`, or use `precompute()`/`load_feature()`. | Build it in a future phase if a maintainer requests it — it would be a thin façade over pieces that already exist, not new logic. |
| 12 | Is `FlatFilesSource` (`data_universe/sources/flatfiles.py`, `PLAN.md` §2) still wanted? | No S3 bulk download or `download_options_day_aggs()` exists. `POLYGON_FLATFILES_ENDPOINT`, `POLYGON_S3_ACCESS_KEY`, `POLYGON_S3_SECRET_KEY` are read by `config.py` and the `s3` extra (`boto3`) is already declared in `setup.py`, but nothing consumes any of it yet. | Not built in any of Phases 1-7. | Build it in a future phase if bulk options history is actually needed; until then, `PolygonOptionsSource.daily_close` covers per-contract, per-day lookups one at a time. |
| 13 | Has the version-bump rule (`PLAN.md` §0) actually been followed? | Consumers pinning by version won't see any of the 40 commits' worth of changes across 7 phases. | Was not followed through Phase 8 (both stuck at `"0.1.0"`); now bumped to `"0.2.0"`. | See `MAINTENANCE.md` item 1 — keep following the rule on every subsequent change. |
| 14 | When does single-name IV30 land? | `vrp_signal_rv21` and `fwd_vrp_expost` are registered per `PLAN.md` §6 ("provide interfaces and stubs") but call `options/iv30.py`'s stub, which always raises `NotImplementedError` for any ticker but `"SPY"`. | Stubbed, documented, tested (the no-lookahead property test special-cases both names to run against `"SPY"` only). | Owner: vrp-research data track (per `options/iv30.py`'s own docstring — "Lionel"). |
